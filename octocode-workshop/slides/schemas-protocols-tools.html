The previous slide showed the mechanism: the model writes a call, the code runs it. This slide is about writing that schema well, and where it led. The point: a schema was the next step in communicating with agents in a predictable way. It led to function calls, and it ended up with many protocols: MCP, A2A and more. The model never sees your code; all it reads is the schema. The input schema tells it what a valid call looks like; the output schema tells it what comes back, so it can read the result and plan the next step. That contract is what made tool calls possible, and once everyone described tools the same way, a shared protocol could follow. Click 1: the lesson, in code. The description strings ARE the prompt the model reads when it fills arguments, an enum removes a whole class of invented values (the highlighted string is what the model sees), and SearchOut is the shape of what comes back. A vague schema gets invented arguments; a typed schema gets reliable calls. Quote to say aloud: Anthropic, "Writing effective tools for agents" (anthropic.com/engineering/writing-tools-for-agents, 11 Sep 2025): "Even small refinements to tool descriptions can yield dramatic improvements"; "think of how you would describe your tool to a new hire on your team". Their later tool-use examples raised accuracy "from 72% to 90% on complex parameter handling" (anthropic.com/engineering/advanced-tool-use, 24 Nov 2025).
