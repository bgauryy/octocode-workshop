Schemas let the LLM call real code

A schema describes a function's input, so the model can ask deterministic code to do the work.

{ "name": "get_time", "description": "Current time in a timezone", "parameters": { "tz": { "type": "string" } } }
get_time({ "tz": "Asia/Jerusalem" })

The previous slide ended on structure inside prompts. Schemas took that structure one step further: they let the model talk to code. The point: a schema is the input of a function, written so the model can read it. Once the model learned to fill that input, it could ask real code to do things it cannot do alone. Click 1: the schema. A name, a description and typed parameters. The model never sees the function body; it reads only this, and the description string works as the prompt for when to use it. Click 2: the model doesn't run anything. It writes a call, valid JSON that matches the schema, here get_time with a timezone. Click 3: your code runs it. That part is deterministic: same input, same output, no guessing. A model can't know the current time; a clock function can. Click 4: the result goes back into the context window, and the model answers from real data instead of predicting it. Click 5: this is what gave LLMs new powers: the time, a web search, reading a file, querying a database. It's also why we could build protocols on top: once every tool is described by a schema, any agent can call any tool the same way. Source for the mechanism: OpenAI, "Function calling and other API updates" (openai.com/blog/function-calling-and-other-api-updates, 13 Jun 2023), where the model returns a JSON object with the arguments and the developer's code calls the function.
