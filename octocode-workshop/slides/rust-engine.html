// meta: researched with Octocode, and now one engine serves MCP and the CLI.
What moved: everything that does work (search, AST, the LSP client, the GitHub client, redaction, caching and response rendering) into one Rust workspace, packages/octocode-native, version 20.2.0 (dev build, unreleased; npm latest is 20.1.0): five crates (Cargo.toml:2): engine (search, structural/AST, LSP, minify, graph, security), github (transport, retry, rate budget, search), runtime (tools, config, cache, providers, response), runtime-napi (the Node adapter octocode-mcp loads in-process) and cli (the binary). The diagram draws as I talk: MCP and the CLI are now thin hosts over the same runtime: "MCP and npx octocode <toolName> share the same schemas, runners, validation, response envelope, pagination, and secret redaction" (docs/OCTOCODE_MCP.md:3). Press → for each pair of bars, and be precise about what they measure. Steps 1–2 come from packages/octocode-native/README.md:267-270: running the native binary directly vs going through the `octocode` Node launcher, which runs the same native engine, so it's launcher overhead: help/auth ~8 ms vs ~120 ms, a tool call ~160 ms vs ~330 ms (no sample size given). The native binary ships inside the npm package as per-platform optional dependencies (packages/octocode-native/package.json:45-52); `npx octocode` starts it through a Node launcher that declares Node ^24.15.0 (other versions only print an engine warning). Step 3 is from CHANGELOG.md:215-217: the first lspSearch in a workspace starts a private per-workspace language server that later CLI calls reuse, so a TypeScript hover goes from ~3 s cold to ~0.1 s warm. Extra from the history: the first Rust crate was the secret scanner, with the same 309 patterns, 20–27× faster than the JS version on clean content (1 MB: 50 ms → 2.1 ms) (git e1ad2d510: packages/octocode-security/README.md:14-40).
