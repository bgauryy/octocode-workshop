Why I built it, in my words: "VladT idea: best for roasting". The crowd favourite. The problem: code reviews are either polite and vague or harsh and unproven. This one is harsh and cited, with a repair path for every finding. Walk the pipe: TARGET: explicit user targets first, widen only when none exist or the user approves; INSPECT the code and verify each significant finding with octocode-research (SKILL.md:40); INVENTORY: rank by demonstrated impact; AUTOPSY the highest-impact offender, "not the funniest one" (references/roast-playbook.md:29); CHECKPOINT: critique only stops here, authorized fixes go to REDEEM (skills/octocode-roast/SKILL.md:10-15). Press → for the sin catalog: Capital offense (critical) → Felony (high) → Crime (medium) → Slop (low) → Misdemeanor (minor) (references/sin-catalog.md:7-13). Two rules make it safe to use: "Punch the code, not the coder" and "Cite or drop it: every major finding needs an exact anchor, mechanism, impact, confidence, and repair move" (SKILL.md:19-20). Savage or nuclear tone only on explicit request (:24). Each finding ends with "Roast: {one evidence-specific line}" (roast-playbook.md:17-25); big targets can be split across parallel workers per domain: security, architecture, performance (references/parallel-roasting.md:8-21). Story: the idea came from VladT (speaker's note). Invoke: npx octocode skill install octocode-roast, then, for example (illustrative prompt): "Roast packages/core. Be savage."
