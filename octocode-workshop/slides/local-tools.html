From the brief: I wanted the same mechanism I had for GitHub on my local code, because the Octocode flow felt better than plain fetch-files-and-rg: same batching, core schema, hints, pagination. Walk the pipe as it draws. It is the research loop from the CLI guide, "map cheaply → search narrowly → read exact evidence → follow symbols or history" (packages/octocode/docs/OCTOCODE_CLI.md:114): structureSearch maps the tree or finds files; localSearch finds literal/regex text and astSearch finds code shape; localFetch reads exactly the lines you need with matchString, ranges or a whole declaration; lspSearch follows the symbol. The line underneath: every row carries next.* (the unread rest, snapshot-pinned) and opt-in hints.* leads, so the agent's next call is already written (docs/OCTOCODE_PROTOCOL.md:88-93). Press → for before/after. Before means whole files and rg's raw match dumps, with no next step, measured in Octocode's scripted tool benchmark (docs/OCTOCODE_PROTOCOL.md:133,135): with hostile input, rg leaked 3 of 3 fake secrets, Octocode 0 of 5, because the native scanner reads every byte bound for the model; a 3.2 MB file costs an 18k-character first page and a 2 MB minified line costs 710; and on plain local questions it matches rg's accuracy, 14 of 15, with about 8% more characters for the citable line gutter. Honest negative: rg answers in 3 to 25 ms, the CLI starts in about 200 ms per call (OCTOCODE_PROTOCOL.md:139). Dates: local tools landed inside octocode-mcp in v11.0 on 27 Dec 2025 (commit 0bef8ac76 "Add local tools (#254)") as localSearchCode, localGetFileContent, localFindFiles and localViewStructure; today's names came with v20. OpenAI's Codex system prompt standardises on ripgrep too ("prefer using `rg` … because `rg` is much faster"; github.com/openai/codex codex-rs/core/gpt_5_codex_prompt.md:5). Text search runs in-process on ripgrep's crates: grep-searcher, grep-regex, grep-pcre2, ignore (ledger L3). Press → again for the two wins: secrets are removed by default, not as an opt-in, so local research is safe out of the box; and the agent gets ONE flow, Octocode, for local and external code: same calls, same schema, same next/hints, whether it reads the workspace or GitHub and npm. Extra: walking pages of a big search now reuses a snapshot instead of rescanning: median 6,340 → 1,847 ms, −71%, 7 alternating reps (the local-tools improvement plan at commit b9cfc4c72, lines 152-155).
