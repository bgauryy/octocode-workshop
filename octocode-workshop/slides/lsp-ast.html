A real run on Octocode's own repo, 9 Oct 2026 (octocode 20.2.0). Left: `octocode localSearch` for the text "exit_code" in packages/octocode-native/crates/cli returns 26 hits in 4 files. Only 4 are the function I mean, fn exit_code(class: ExitClass) at cli/src/cli/mod.rs:722 and its 3 uses. The other 22: a test helper with the same name, fn exit_code(output: &Output) at tests/cli.rs:17, with 19 uses (20 hits); a method call error.exit_code() at mod.rs:146; and the substring in mod cli_exit_codes at tests/main.rs:17. A text-only agent "finds 26 callers" and edits the wrong ones. Press →: `octocode lspSearch` with operation references, symbolName exit_code, line 722 asks rust-analyzer, and returns 4 locations in 2 files: the definition plus mod.rs:673 and serve.rs:366 and :371. (Honest detail: about 13 s on the first, cold call. Even the tool tells you what it couldn't see: when feature-gated Rust code could hide references, it flags isPartial with partialReasons cfgGatedFiles (docs/OCTOCODE_TOOLS.md:657); this run came back complete.) This is the server instruction (ledger L2): "Identity (callers, references): lspSearch with a hit's symbolName+line." Press → for the takeaway: text finds the name, LSP finds the symbol, AST finds the code shape. AST: tree-sitter grammars + ast-grep (+ Oxc), 11 language families (ledger L3); structural patterns like $X.unwrap() "match code shape, never comments or strings" (docs/OCTOCODE_PROTOCOL.md:97-99), and the same parse feeds `octocode graph` for callers, impact and cycles. Measured in the scripted benchmark: "LSP references are exact (rg -w: 0.26–0.62)"; symbols exact on 6 of 6 files vs 0.81–0.98 for regexes and ctags (docs/OCTOCODE_PROTOCOL.md:132). lspSearch operations (ledger L1): definition, references, callers, callees, hover, typeDefinition, implementation, workspaceSymbol, supertypes, subtypes, diagnostic, documentSymbols; servers for TypeScript, Python, Rust, Go, Java, C/C++, C#, Scala. Outside evidence that structure beats flat text: LocAgent's graph-guided localization reaches "up to 92.7% accuracy on file-level localization" (arXiv:2503.09089, 12 Mar 2025).
