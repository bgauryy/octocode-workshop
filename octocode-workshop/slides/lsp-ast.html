TL;DR first. LSP, the Language Server Protocol, is what your editor uses for "go to definition" and "find all references": a language server (rust-analyzer, the TypeScript server…) understands the code, not just its text. Octocode's lspSearch asks the same servers and hands the answers to the agent. Why we needed it, a real run on Octocode's own repo, 9 Oct 2026 (octocode 20.2.0): `octocode localSearch` for the text "exit_code" in packages/octocode-native/crates/cli returns 26 hits in 4 files. Only 4 are the function I mean, fn exit_code(class: ExitClass) at cli/src/cli/mod.rs:722 and its 3 uses. The other 22: a test helper with the same name, fn exit_code(output: &Output) at tests/cli.rs:17, with 19 uses (20 hits); a method call error.exit_code() at mod.rs:146; and the substring in mod cli_exit_codes at tests/main.rs:17. A text-only agent "finds 26 callers" and edits the wrong ones. Press →: `octocode lspSearch` with operation references, symbolName exit_code, line 722 asks rust-analyzer and returns 4 locations in 2 files: the definition plus mod.rs:673 and serve.rs:366 and :371. (Honest detail: about 13 s on the first, cold call. When feature-gated Rust code could hide references, the tool flags isPartial with partialReasons cfgGatedFiles (docs/OCTOCODE_TOOLS.md:657); this run came back complete.) Measured in the scripted benchmark: "LSP references are exact (rg -w: 0.26–0.62)" (docs/OCTOCODE_PROTOCOL.md:132). Press →: the four questions it answers around one symbol. Definition: where is it defined, so the agent opens the real source, not a same-named copy. References: every use, checked before a rename. Callers: who calls it, so you know what a change breaks. Callees: what it calls, to trace the flow down. Search tells the agent what a thing is called and where it lives; LSP adds how code connects. Press →: how the agent uses it. The server instruction (ledger L2): "Identity (callers, references): lspSearch with a hit's symbolName+line." So a search hit gives the name and line, lspSearch follows the symbol, localFetch reads the exact lines. All lspSearch operations (ledger L1): definition, references, callers, callees, hover, typeDefinition, implementation, workspaceSymbol, supertypes, subtypes, diagnostic, documentSymbols; servers for TypeScript, Python, Rust, Go, Java, C/C++, C#, Scala. Alongside it, astSearch finds code by shape: tree-sitter + ast-grep, 11 language families (ledger L3). History: LSP arrived 10 Jan 2026 in v11.1.0 as lspGotoDefinition / lspFindReferences / lspCallHierarchy (commit 28f1ecb23). Next: the missing piece, my own skills.
