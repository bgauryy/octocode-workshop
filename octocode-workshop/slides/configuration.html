GitHub token: first found wins · env var may come from .env

  1. GH_TOKEN / GITHUB_TOKEN

  2. octocode auth login

  3. gh auth token

Precedence, from docs/CONFIGURATION.md "How settings override each other" (https://github.com/bgauryy/octocode/blob/main/docs/CONFIGURATION.md). The rows draw top to bottom in that order. First, the shell environment or your MCP client's env block: those always win. Then <project>/.octocode/.env, then ~/.octocode/.env: these hold tokens and API keys, and the CLI and MCP server load them. Then <project>/.octocode/.octocoderc and ~/.octocode/.octocoderc: the settings files, workspace beating home. Last, the built-in defaults. Press → for the rule: env beats files, project beats home, and misconfiguration never blocks startup; a bad value is skipped with one stderr warning. Press → for tokens: the GitHub token is the first credential found: a token variable (GH_TOKEN, then GITHUB_TOKEN) from the shell, the workspace .env or the home .env, in that order of source; then the octocode auth login credential; then the OS credential store; then gh auth token (docs/AUTHENTICATION.md:14-22). A token variable always beats a stored login, and .octocoderc never holds a GitHub token. Some keys (for example ALLOWED_PATHS, WORKSPACE_ROOT) are home-only and skipped in a workspace file (docs/CONFIGURATION.md:69). That last step is why gh auth login is enough for most people.
