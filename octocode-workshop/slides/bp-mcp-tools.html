Recap · best practices for building tools

Tool design is prompt design

Every word the model sees from your tool steers its next move.

  1. Description

    • When to call it
    • What it does and returns

  2. Schema

    • Fields explain themselves, not their name
    • query: "The query"
      query: "Regex to search"

  3. Result

    • Lean: only what's needed
    • Paginate when it's large
    • Smart errors say how to fix
then measure and refine
General rules for any tool an agent calls, whether MCP, CLI or function calling. The model only knows your tool through the text you give it, so tool design is prompt design. Press → (description): say when to call the tool and what it does and returns. Octocode writes descriptions in one grammar: prose says what the tool does and when it is right, an optional <empty> gives the repair, and one <workflow> names where the output goes next (docs/OCTOCODE_PROTOCOL.md:66). Press → (schema): every field description adds meaning beyond its name. "query: The query" tells the model nothing; "Regex to search" tells it how to fill it. Keep inputs minimal and typed, enums over free strings. Press → (result): lean results, only what the next step needs. Octocode returns matching windows, not whole files, with gap markers like "... [lines 22-875 not requested] ..." (crates/runtime/src/tools/local_fetch/extraction.rs:46-48). Paginate large results instead of dumping them. Smart errors: on empty or failed results, one short hint that says how to fix it, for example an empty localSearch says "No matches in 12 files searched." (crates/runtime/src/tools/local_search/leads.rs:1246-1252) and its description carries the repair: "Lowercase/shorter term, regex:"rust", includeIgnored." (octocode schema localSearch; ledger V8), not a stack trace. Press → (the loop back): then measure with a fresh agent and refine. Next: writing skills, where the trigger comes first.
